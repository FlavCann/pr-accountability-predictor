The idea: an exam for the pipeline

The pipeline reads investor presentations and pulls out the promises a company makes. When you change something about it — a newer model, a reworded prompt, different chunk sizes — you need to know one thing: is it actually better, or does it just look better?

Reading a handful of outputs and forming an impression can't answer that. So the pipeline sits the same exam every time and is marked the same way. The rest of this guide is the exam, the marking, and the rules that stop the pipeline cheating.

Building the exam

People do this, occasionally. The transcripts are divided into three piles before anyone labels them, and a transcript never moves between piles afterwards.

Why three piles?

Examples. A student who has already seen the answers isn't being tested. The prompt shows the model a few example sentences, and those came from these four transcripts, so they are never used as exam questions.

Dev and test. If you tweak the prompt over and over against the same exam, you slowly tune it to that exam, like memorising past papers. Dev is where you practise; test is the exam you don't practise on, and it decides promotions.

The masked lines

Every transcript we have supplied at least one prompt example. The two test transcripts supplied exactly one each, so that one passage is blanked out (masked) and the rest of the transcript is still used. Anything the model says about a masked passage is ignored.

What labelling means

A person reads a whole transcript, Q&A included — about 10–13 thousand words, roughly one to two hours — and for every promise records the exact words, what kind of promise it is, and how firmly it was stated. Tempting non-promises (a joke about the catering, "we will continue to monitor") are recorded too, as things the model must not pick out. The full rules are in evals/GUIDELINES.md.

Test transcripts are labelled blind: without looking at anything the model said about them, so the key isn't nudged towards the model's opinion.

Each time you change something

This is the loop you'll run again and again. Change one thing, run python -m pr_predictor eval, and read the verdict.

The exam is sat three times because a model gives slightly different answers each run. Three runs show how much the score wobbles on its own, so a wobble isn't mistaken for improvement.

Every run is written down with a manifest: which model, the exact prompt text, the settings, and fingerprints of the code. Months later you can still say exactly what produced a score.

What the referee checks

The gate runs these in order and stops at the first one that fails. The reason is printed, so a block always tells you what to do next.

  1. Did the model find anything the answer key doesn't cover?Those "not in the key" answers might be real promises nobody labelled. A person must label them first; otherwise nobody knows whether the model was right.
  2. Is it the same exam, marked the same way?If the answer key or the marking code changed, old and new scores aren't comparable. Re-run the champion on the new exam first.
  3. Did only one thing change?Swap the model and the prompt together and you can't tell which one helped. Change one of: model, prompt, code and settings.
  4. Can every answer still be traced to the transcript?If fewer answers point to real words, it's blocked whatever the score. A claim about a company that can't be cited is unacceptable here.
  5. Did it pick out more of the known traps?The catering joke and friends. More of these is blocked.
  6. Is the score higher by more than luck would explain?With at least five scored transcripts, the whole likely range of the improvement must sit above zero. With fewer, it compares the raw scores and labels the verdict UNDERPOWERED.

The numbers, in plain words

An answer counts as correct when it covers at least half of a promise in the key. The model doesn't have to pick exactly the same start and end words as the person did.

NumberPlain meaningWhy it matters here
PrecisionOf the things it called promises, how many really were?Low precision means accusing a company of promises it never made.
RecallOf the real promises, how many did it find?Low recall means commitments slip through unnoticed.
F1One number that balances the two. The headline score.What the referee compares.
Span fidelityCan every answer be pointed to in the transcript?Must never go down. It's the product's promise to users.
Type, hedge, deadline accuracyFor promises it found: right kind, right firmness, right date?Reported for insight; the referee doesn't decide on them.
Likely range"The true score is probably between X and Y."Wide range = too little evidence to be sure.

Why "UNDERPOWERED"?

Flip a coin 4 times and get 3 heads: you can't conclude the coin is unfair. Flip it 400 times and get 300: you can. Each labelled transcript is another flip. With 4 scored transcripts the system can't yet tell luck from real improvement, so it says so rather than pretending. More labelled transcripts fixes this.

Tracking progress over time

Every run goes on the scoreboard. Over months that becomes a history of everything you tried and why the pipeline is the way it is. The champion only moves when a run earns it.

Two things to notice. Run #7 scored higher than the champion and was still blocked: its likely range includes "no improvement at all". And the score went down at #5 without anything getting worse — the exam got harder and more complete, which is why scores are only ever compared on the same exam.

Every stage has its own exam

Finding promises is only the first step. Each later step is tested separately and fed the correct input from the answer key, so a mistake in an early step is never blamed on a later one.

Find promises

eval

Answer key: 10 promises in 2 dev transcripts, plus 2 test transcripts in progress.

F1, span fidelity. Decides promotions.

Group restatements

eval-threads

Does it recognise the same promise said twice? A moved deadline must stay separate.

Pair score; any wrongly merged revision fails outright.

Decide kept or missed

eval-adjudication

Given a promise and the evidence, is the verdict right? Needs cases written by a person.

Verdict accuracy. No cases yet.

Predict the future

eval-predictions

Marked by reality: when a deadline passes, we find out whether the prediction was right.

Brier score and calibration. Nothing resolved yet.

The last one is the most trustworthy exam of all, because nobody can cheat on the future. Only predictions made before their deadline count.

There's also an optional judge (eval --judge): a different AI model checks that each promise's one-line summary says what the speaker said. It is never used by the referee until it has been checked against a person's judgement.

Not measured yet: how well the pipeline finds evidence for a verdict, and fetching transcripts (covered by code tests only).

Glossary

Benchmark / eval
A fixed exam with an answer key, used to compare versions fairly.
Gold set
The answer key: promises a person has marked in transcripts.
Harness
Everything around the model: the code that chunks transcripts, calls the model and checks its answers.
Split
Which pile a transcript is in: examples, dev, test (or fresh, for transcripts newer than the model's training).
Leakage / contamination
The model having seen exam answers — for instance a prompt example taken from an exam transcript. The eval refuses to run when it detects this.
Mask
A blanked-out passage that is never scored, used for the one example sentence in each test transcript.
Labelled blind
Labelled without seeing the model's answers first, so the key isn't nudged towards the model.
Exhaustive
Every promise in a transcript is labelled. Only then is precision fully trustworthy.
Unjudged
Something the model found that the key doesn't cover. A person must label it before the referee will promote.
Repeats
Running the same exam several times to see how much scores wobble on their own.
Likely range
The spread the true score probably lies in (a "confidence interval"). Narrows as more transcripts are labelled.
Underpowered
Too few exam papers to tell a real improvement from luck.
Champion
The best version so far — the bar every new run must beat.
Gate
The referee: the rules that decide whether a run beats the champion.
Manifest
The label on each result saying exactly what produced it: model, prompt, settings, code.
Slice
A tagged subset of promises (fiscal-year deadlines, Q&A, garbled words) scored separately, so a weakness shows even when the average doesn't move.
